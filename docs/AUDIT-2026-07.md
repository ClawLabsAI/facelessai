## 🔴 Hallazgos críticos (bloqueantes)

### C1 · Móvil roto por conflicto de especificidad CSS
- **Evidencia:** `.sidebar{...left:0}` (línea 32, especificidad 0,1,0) gana a `aside{left:-260px}`
  del `@media(max-width:768px)` (línea 319, especificidad 0,0,1). Las media queries **no** añaden
  especificidad.
- **Efecto medido en navegador:** la sidebar queda `position:fixed; left:0` ocupando **220px**
  permanentemente. En un móvil de 375px se come el 59% de la pantalla. El botón hamburguesa y
  `aside.mob-open` quedan inútiles.
- **Fix:** cambiar el selector del media query a `aside.sidebar{left:-260px}` (1 línea).
- **Severidad:** crítica — hoy la app es inusable en móvil, y el tráfico de un producto así es
  mayoritariamente móvil.

### C2 · Backend sin autenticación ni rate limiting, con CORS abierto
- **Evidencia:** `main.py` → `allow_origins=["*"]`, y `grep` de `Depends|HTTPBearer|X-API-Key|rate_limit` = **0**.
- **Efecto:** cualquiera que descubra la URL del backend puede lanzar renders de vídeo ilimitados
  → consumo de CPU/disco y **coste directo** en tu hosting. Es una granja de render abierta.
- **Agravante:** los jobs viven en un dict en memoria y no hay limpieza de `TEMP_DIR` → llenado de disco.
- **Fix:** API key compartida por cabecera + rate limit por IP + CORS restringido al dominio de Pages.
- *Mitigado ya:* sin inyección de comandos (usa listas, no `shell=True`) ni path traversal.

### C3 · Sin escapado HTML (XSS) ni CSP
- **Evidencia:** función de escape = **NO**, `innerHTML` = **194 usos**, CSP = **NO**.
- **Vector real:** las respuestas de la IA se renderizan con `innerHTML`. Una web analizada por
  "Espía de canales" o "URL→Vídeo" puede contener *prompt injection* que haga a la IA devolver
  HTML/JS, que se ejecuta en la app **con las claves del usuario en localStorage**.
- **Fix:** helper `escapeHtml()` en los puntos que pintan datos externos/IA + meta CSP.

### C4 · No se puede vender: sin usuarios, sin cobro
- **Evidencia:** vistas `saas-users/billing/plans/admin/onboarding` son texto "Próximamente"
  (9 ocurrencias). Sin Stripe, sin Supabase, sin login. Todo el estado es `localStorage` de un
  único navegador.
- **Efecto:** no hay forma de registrar un usuario ni de cobrarle. Los planes (Free/Pro 29€/
  Agency 99€) son HTML estático sin lógica ni límites aplicados.

### C5 · No hay landing page
- **Evidencia:** `index.html` **es** la app. Un visitante de `clawlabsai.github.io/facelessai/`
  aterriza directamente en un dashboard de ceros, sin propuesta de valor, sin explicación, sin CTA.
- **Efecto:** conversión ≈ 0. Es el mayor bloqueante de captación junto con C4.

## 🟡 Hallazgos medios

- **M1 · Rendimiento:** 900KB en un archivo, 4035 nodos DOM, todas las vistas montadas. En local
  carga en 80ms, pero en móvil 4G real el FCP será pobre. Ya hay memoización y carga diferida parciales.
- **M2 · Calidad de texto ES:** ~10 cadenas sin acentos ("Configuracion", "Automatizacion").
- **M3 · Sin analítica de producto** (GA/Plausible/PostHog) → saldrás al mercado a ciegas, sin saber
  dónde abandonan los usuarios.
- **M4 · Sin `rel="noopener"`** en enlaces `target="_blank"` (tabnabbing).
- **M5 · Vista "Reutilizar contenido"** sigue siendo maqueta con datos falsos (ya redirige honestamente,
  pero ocupa un hueco de navegación sin aportar función).

## 🗺️ Plan de sprints hacia 9/10

> Precondición estratégica: elegir modelo de distribución (ver "Decisión pendiente" abajo).
> El plan asume **SaaS multi-usuario**; la variante BYOK se indica en cada sprint.

### Sprint 0 — "Parar la hemorragia" (1–2 días) 🔴
Objetivo: que nada esté roto ni expuesto.
1. Fix móvil C1 (`aside.sidebar` en media query) — 1 línea.
2. Backend C2: API key por cabecera + rate limit por IP + CORS al dominio real + limpieza de `TEMP_DIR`.
3. XSS C3: `escapeHtml()` en render de datos externos/IA + meta CSP + `rel="noopener"`.
4. Limpieza de repo A8: borrar dashboards V2/V3/V4, `files.zip`, `replace_nav.py`; añadir LICENSE.
- **Resultado:** Seguridad 3→7, Responsive 3.5→8.

### Sprint 1 — "Primera impresión" (1 semana) 🔴
Objetivo: que un desconocido entienda y pruebe el producto.
1. **Landing page** (`landing.html` como raíz, app en `/app`): propuesta de valor, cómo funciona,
   demo visual, precios, FAQ, CTA. Mantiene el deploy de archivo único.
2. **Onboarding real** (arreglar A1): wizard de 3 pasos → idioma/nicho → clave API → primer vídeo.
3. **Modo demo** (A7): datos de ejemplo etiquetados como demo + botón "limpiar demo", para evaluar
   sin claves.
4. **Separar demo de real** (A4): etiquetar visualmente todo dato ficticio.
5. README decente + capturas.
- **Resultado:** Landing 0→8, UX 4.5→7, Demo 1→8, Contenido 4→7.

### Sprint 2 — "Ser encontrado" (4–5 días) 🟠
1. SEO completo (A2): meta description, OG/Twitter, favicon, canonical, JSON-LD `SoftwareApplication`,
   `<h1>`, `sitemap.xml`, `robots.txt`.
2. Analítica de producto (M3): Plausible o PostHog + eventos clave del embudo.
3. i18n real (A3): diccionario ES/EN + `data-i18n` en la UI (empezar por landing y onboarding).
- **Resultado:** SEO 1→8, Marketing 0.5→6, Idiomas 1.5→7.

### Sprint 3 — "Poder cobrar" (2 semanas) 🔴
1. Auth con Supabase (email + OAuth Google).
2. Migración de `localStorage` a sincronización con Supabase (con modo offline).
3. Stripe Checkout + portal de cliente + webhooks.
4. Aplicación real de límites por plan (vídeos/mes, canales) — hoy los planes son decorativos.
- **Resultado:** Usuarios 1→8, Monetización 1→8, Negocio 2→8.

### Sprint 4 — "Operar el negocio" (1 semana) 🟠
1. Panel admin real: usuarios, suscripciones, uso, errores.
2. Facturación y recibos.
3. Emails transaccionales (bienvenida, fin de trial, fallo de pago).
- **Resultado:** Admin 1→8.

### Sprint 5 — "Pulido para escalar" (1 semana) 🟡
1. Accesibilidad (A5): labels, aria, landmarks, foco visible → objetivo WCAG AA.
2. Rendimiento (M1): dividir CSS/JS críticos, lazy-load de vistas pesadas, comprimir.
3. Centro de ayuda (A6): guías, FAQ, tooltips contextuales, vídeo de 90s.
4. Textos ES revisados (M2).
- **Resultado:** A11y 3→8, Rendimiento 5.5→8, Ayuda 1.5→8.

**Duración total estimada: 6–7 semanas** hasta un 8.5–9/10 medio con producto vendible.

## ❓ Decisión pendiente (condiciona todo el plan)

**¿SaaS multi-usuario o producto BYOK?**

- **A) SaaS multi-usuario** (plan de arriba): tú pones la infraestructura y las claves, cobras
  suscripción. Mayor ingreso recurrente, pero exige Sprints 3–4 completos, asumir el coste de las
  APIs y soporte. ~6-7 semanas.
- **B) BYOK / licencia** ("Bring Your Own Key"): el usuario pone sus propias claves (como ahora).
  Vendes licencia o pago único con Gumroad/Lemon Squeezy. **La arquitectura actual ya encaja
  perfectamente** — te saltas casi todo el Sprint 3. ~2-3 semanas al mercado.

La arquitectura actual (localStorage + claves del usuario) es **ideal para B** y **contraria a A**.
Si el objetivo es "salir al mercado con seguridad y pronto", **B es el camino corto**; A es el
camino de mayor valor a largo plazo.
